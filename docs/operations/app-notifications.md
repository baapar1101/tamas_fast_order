# Customer app notifications

Admin entry: `/admin/app-notifications`, in Customers and Communications. Admins have access automatically; operators need the separate `manage_app_notifications` permission in Access Groups.

An operator saves a draft, previews the current audience, then confirms sending. Title, message, a whitelisted native destination, all active customers or selected customer IDs are configurable. Admins, operators, inactive/deleted customers and invalid/disabled login sessions are excluded from sending. Customers without an active registered device appear as skipped. Counts distinguish customers from devices; each history row represents one device, or one skipped customer without a device. The existing table export supplies Excel export of visible history rows.

Campaign content becomes immutable after queuing. A revision and audience fingerprint prevent sending an outdated preview, and a locked transaction prevents double-clicks or concurrent requests from creating duplicate delivery rows. History offers status filtering, timestamps, recipient details, cancellation of pending sends, retry of definitively failed sends and copying a campaign to a new draft. Retry rechecks the original device's current owner/session/token and never retries accepted or uncertain results. An already in-flight notification cannot be recalled.

Migration `0030_native_campaigns` adds only `native_campaigns` and `native_campaign_deliveries`. The existing scheduler claims durable pending rows using database locks. No new service, cron or process is needed. A worker interruption/ambiguous network result is recorded as unknown rather than automatically resending a possibly accepted notification. Queue and content metadata are recorded in the existing admin audit log; raw device tokens and session hashes are not exposed in history responses.

FCM acceptance is distinct from a confirmed app receipt/open. APK 1.0.2 sends idempotent authenticated acknowledgments bound to the original customer, installation and login session. Background Android notifications may not report receipt until opened. No receipt means unconfirmed, not necessarily undelivered. The campaign message is intentionally visible in the notification; existing automatic financial/identity notifications retain their generic private text. Destinations are fixed native pages, not arbitrary external URLs. Older APKs still display messages and route supported event prefixes, but the new destinations and receipt/open history need 1.0.2.

## Verification and deployment

`scripts/check-native-campaigns-isolated.ts` requires a separate disposable `tamas_native_qa_YYYYMMDD` database and matching role, and blocks external traffic. Sixteen checks cover permissions, invalid recipients/destinations, active audience counts, stale previews, concurrent queueing, transport statuses, token rotation on retry, ownership, idempotent receipts, cancellation, expired sessions, zero reachable devices, interrupted workers and redacted history. It is never run against production.

The real admin UI and standalone QA APK were tested with synthetic accounts. Two custom notifications reached the emulator through real FCM: selected-recipient Wallet in foreground, and all-recipient Discounts in background. The panel recorded actual received/opened timestamps and correctly skipped the unconnected synthetic customer. Dark desktop and light mobile (390px viewport) were visually checked; the page and modal had no horizontal page overflow. No messages were sent to real customers during verification.

Build shared/API/web, apply migration 0030, then restart the existing aaPanel-managed API and reload the checked Nginx download configuration. Publish the signed `tamas-market-1.0.2.apk` at its versioned URL, preserving earlier releases. The normal APK build forces HTTPS/production origin and keeps QA artifacts separate. Stop and remove the disposable QA database, role, process, tunnel and credentials afterwards.
