# پیگیری مدارک مفقود و درخواست جایگزین

## محل استفاده

- مدیریت: «فروش و سفارش‌ها ← مدارک مفقود و تکمیل پرونده» در `/admin/document-recovery`، و تب همان نام در اعتبارسنجی. مجوز `manage_users` لازم است.
- حساب کاربر: «مدارک و درخواست‌های تکمیل» در `/account/documents`. درخواست باز در صفحات حساب نیز اعلان دارد؛ فقط درخواست‌های همان حساب نمایش داده می‌شوند.
- کنار پرونده‌های اعتباری دارای مدرک مفقود، هشدار نمایش داده می‌شود. کتابخانهٔ عمومی رسانه همچنان مدارک خصوصی را نشان نمی‌دهد.

## روش کار

۱. بررسی وجود اصل و بندانگشتی از فضای خصوصی انجام می‌شود؛ فهرست شامل فایل سالم، مفقود، خطای فنی دسترسی و نسخهٔ جایگزین‌شده است. خطای دسترسی فنی به‌تنهایی مجوز درخواست مجدد نمی‌دهد. فیلتر پیش‌فرض «نیازمند پیگیری» است و فایل تازه‌مفقود نیز بدون تغییر کد شناسایی می‌شود.

۲. مالک ابتدا از ارجاع‌های کارت ملی/جواز/چک/گزارش/رسید/سفارش مشخص می‌شود و با مالک آپلود تطبیق دارد. تعارض یا مالک نامشخص، درخواست را مسدود می‌کند. «بدون ارجاع فعال» صریحاً مشخص است: این فایل لزوماً مدرک پروندهٔ فعلی نیست. نقش مدیر/اپراتور نیز نباید با مشتری اشتباه شود.

۳. مدیر برای هر مدرک، متن درخواست را بازبینی و ثبت می‌کند. تنها یک درخواست باز برای یک فایل ممکن است. درخواست همیشه در حساب ذخیره می‌شود؛ پیامک، تلگرام و بله انتخاب‌های اختیاری و پیش‌فرض خاموش‌اند. تنظیمات سرویس و ترجیحات اعلان مشتری رعایت می‌شوند. نتیجهٔ پذیرش/عدم ارسال/خطای هر کانال جداگانه ثبت می‌شود؛ پذیرش سرویس به معنای تحویل قطعی نیست. متن بیرونی فقط ارجاع به بخش حساب دارد، نه فایل یا اطلاعات داخل مدرک.

۴. مشتری فایل را خصوصی آپلود و برای بررسی ثبت می‌کند. فایل حساب دیگر، فایل قبلیِ مفقود یا فایل غیرقابل‌خواندن پذیرفته نمی‌شود. اصل پرونده در این مرحله تغییر نمی‌کند.

۵. مدیر می‌تواند مدرک را تأیید کند، با علت رد کند تا مشتری دوباره بفرستد، یا درخواست را لغو کند. همهٔ نسخه‌های ارسالی و علت‌ها محفوظ‌اند. تأیید با قفل تراکنشی و تطبیق دقیق مقدار قبلی، تنها ارجاع مدرک را تغییر می‌دهد؛ شناسهٔ ۸ با ۸۰ اشتباه نمی‌شود. وضعیت مالی رسید، مبلغ سفارش، سقف اعتبار و وضعیت پرونده تغییر نمی‌کنند.

۶. جایگزینی گزارش ICS24 به PDF قابل‌استخراج و تطبیق کد ملی نیاز دارد و نسخهٔ snapshot جدید می‌سازد؛ دادهٔ استخراج‌شدهٔ گزارش قدیمی بازنویسی نمی‌شود. هیچ تصمیم خودکار دربارهٔ اعطای اعتبار در این فرایند وجود ندارد.

## تاریخچه و مجوزها

دو جدول افزایشی migration 0028: `document_reupload_requests` و `document_reupload_submissions`. وضعیت درخواست: pending → submitted → completed؛ در صورت رد، دوباره pending می‌شود؛ cancelled بسته است. نسخهٔ قبلی فایل حذف نمی‌شود. رویدادهای request/submit/approve/reject/cancel در audit_log، در همان تراکنش ثبت می‌شوند.

در baseline انتشار، ۹ فایل مفقود به سه حساب تعلق داشت: هفت فایل از دو حساب مدیریتی و دو فایل از یک حساب مشتری. آن دو فایل مشتری ارجاع فعال نداشتند. نام‌ها و اطلاعات شخصی در مستندات عمومی Git ثبت نشده‌اند و فقط در پنل مجاز دیده می‌شوند. هیچ درخواست یا پیام بیرونی به‌طور خودکار برای این baseline ساخته یا ارسال نشده است.

## آزمون

```sh
npm test
npm run typecheck
npm run lint
node scripts/normalize-ui-tokens.mjs --check
cd apps/api
npx tsx scripts/verify-document-recovery.ts --allow-isolated-schema
```

تست یکپارچه به اتصال دیتابیس با اجازهٔ ساخت schema نیاز دارد. فضای خالیِ موقت با نام `tamas_doc_test_<uuid>` می‌سازد؛ فقط ساختار هشت جدول کپی می‌شود، نه دادهٔ مشتری. پیش از هر INSERT، sequenceهای سریال با identityهای مستقل جایگزین می‌شوند. queryها search_path محدود به schema آزمایشی دارند. دو جدول جدید با migration واقعی ساخته و مالکیت، درخواست/تأیید هم‌زمان، رد و ارسال مجدد، حفظ تاریخچه، جایگزینی دقیق و ثابت‌ماندن مالی آزموده می‌شوند. در پایان schema و فایل‌های صرفاً آزمایشی حذف می‌شوند؛ سرویس تولید و داده‌های آن تغییر نمی‌کنند.

در انتشار ۲۳ اکتبر ۲۰۲۶ تست‌های محلی شامل ۳۷ shared، ۷۶ API، ۳۶ web و ۱ payment (۱۵۰ تست) موفق شدند. تست یکپارچهٔ جدا نیز موفق بود. پیش از migration، بکاپ تراکنشی ۴۱ جدول با مجوز 0600 روی سرور گرفته شد:

`/www/wwwroot/tamas_fast_order/apps/api/.private/release-backups/before-document-recovery-1792785914142.json.gz`

این بکاپ JSON فشرده است، نه pg_dump؛ فایل‌های باینری مدارک جزو آن نیستند. برای نگهداری مدارک همچنان [راهنمای خصوصی‌سازی](private-documents.md) معتبر است.
